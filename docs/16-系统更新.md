# 系统版本检查与更新

SkyShield 的更新源是 `Vme18000yuan/SkyShield`，Docker 镜像来自
`solder110/skyshield-*`。界面“关于天穹”会显示部署方式、实际运行的源码提交、
发布版本、发布说明和最近一次更新的阶段与结果。

旧版的本地模式没有注册更新接口，Docker 模式则沿用 LunaFox 发布清单与专用升级器，
与 SkyShield 的部署脚本不匹配。新的入口通过宿主机上的独立更新进程工作，
服务重启不影响其执行与记录。上游 Agent 的镜像和协议版本沿用目标源码中的配置，
SkyShield 产品版本独立使用源码提交标识。

## 首次接入

这一功能需要新版 Server、Frontend 和部署脚本同时安装。旧版无法通过旧的更新按钮
自行引入新升级器，需先在维护时间执行一次正常部署：

```bash
# Git 克隆的源码目录；存在本地修改时先自行提交或保存
git pull --ff-only

# 二选一
./docker.sh pull                       # 使用已发布配套镜像
./local.sh start --no-tools-install    # 本地编译并启动
```

一键部署会启动独立的更新进程。ZIP 下载目录不会自动变为 Git 仓库；界面会提示
自动安装不可用。ZIP 部署可在备份数据库、密钥和配置后迁移到官方 Git 克隆目录，
保持原数据目录及 Docker 项目数据卷，不要同时启动两套实例。

对于长期运行的主机，可将更新进程交由 systemd 管理：

```bash
./update.sh install-service --mode docker
# 或本地部署
./update.sh install-service --mode local
```

该命令应由原部署用户执行；root 部署安装系统级服务，普通用户安装用户级服务。
用户级服务如需开机自动启动、退出登录后继续运行，由管理员为该用户启用
`loginctl enable-linger <用户名>`。服务名带部署目录摘要，避免不同项目相互覆盖。
安装时保留当前代理和本地部署端口/数据目录环境；变更这些配置后重新安装服务。
原有 systemd 服务可通过 `systemctl [--user] status skyshield-updater-*.service` 查看。

不使用 systemd 时可手动管理后台进程：

```bash
./update.sh start --mode docker
./update.sh start --mode local
./update.sh status
./update.sh stop
```

本地模式使用 `.local/updater-local/socket/control.sock`，Docker 模式使用
`.local/updater/socket/control.sock`。两种模式的操作记录和备份分别保留，
并共用部署锁；都通过私有 Unix socket 通信，不对外监听 TCP 端口。Docker 的 Server
只挂载 Docker 模式的通信目录。当两个更新进程同时可访问时，`status`、`check`、
`apply`、`stop` 和 `acknowledge-recovery` 需附加 `--mode local` 或 `--mode docker`。

## 检查和安装

更新进程每小时检查一次稳定渠道。没有发布 `updates/stable.json` 时会明确显示
“尚未发布支持自动更新的稳定版本”，不会误报已是最新，也不会把 GitHub 任意提交当作
可安装版本。连接或解析失败会给出检查失败状态，并要求重新检查。

管理员可以在“关于天穹”点击“检查更新”，查看发布说明后确认“安装更新”。
也可以在部署机使用：

```bash
./update.sh check
./update.sh apply --confirm
./update.sh status
```

安装步骤为：

1. 检查源码无未提交修改、分支可前进、没有扫描或 AI 任务，以及备份和构建空间。
   同一部署一次只接受一个操作；重复请求不会创建第二次更新。
2. 从固定 GitHub 仓库获取发布清单绑定的源码提交。Docker 提前拉取四个应用镜像，
   按摘要固定版本，并核对镜像中的源码提交标签。不会将 `latest` 的后续变化混入本次更新。
3. 阻止新的界面写入，再次检查任务，然后停止应用；数据库、Redis 等保留运行。
4. 生成 PostgreSQL custom-format 备份，保存密钥、`.env`、旧版本信息及本地二进制/前端指针。
5. 本地部署更新依赖、编译并运行迁移；Docker 使用目标源码的 Compose 配置，
   执行初始化、迁移并启动固定摘要的镜像。两种模式都会暂时中断服务。
6. 检查服务就绪、初始化退出码和扫描 Agent 状态，成功后记录版本。前端断线恢复后
   可继续查询状态；完成后点击“刷新界面”。

备份需要额外可用空间：至少数据库当前占用加 10 GiB。实际项目更大时需预留更多。
本地成功升级后保留当前前端构建与更新前构建；成功更新的数据库备份保留最近一次。
失败或需要恢复的操作目录不自动删除。Docker 历史镜像和全局缓存不由更新器清理。

源码是干净但包含本地提交或领先发布分支时，更新器不会强制重置工作目录。
`updates/` 中的渠道记录属于源码发布之后的元数据，可在源码完全一致时保留。
平台设置、数据库、AI 记录和密钥不纳入 Git 更新。

## 失败与恢复

Docker 操作记录位于 `.local/updater/`，本地操作记录位于 `.local/updater-local/`。
两者均包含 `operation.json` 和 `operation-<操作ID>/`；操作目录包含 `update.log`、`previous.json`、
`target.json`，完成备份后还有 `database.dump` 和 `secrets/`。

应用停止之前的失败标记为 `failed`，原服务继续运行；处理原因后重新检查即可重试。
应用停止之后失败，或更新进程意外中断，标记为 `needs_recovery`，不自动重复迁移，
也不将回退程序等同于数据库回退。服务不可访问时，在宿主机运行 `./update.sh status`
并查看该操作日志，按故障阶段选择向前修复或从备份恢复。

数据库备份不包括 AI 工作区、上传文件等文件型业务数据。涉及这些数据格式的发布，
必须在发布说明中写明额外备份/迁移要求。密钥要与加密业务数据一起保留。

恢复时先停止应用写入；依据 `previous.json` 恢复源码，Docker 使用
`previous-images.json` / `compose.release.json`，本地使用 `bin/` 和
`frontend-build.json` 恢复原运行产物。仅在确认需要恢复数据库时才按 PostgreSQL
备份恢复流程使用 `database.dump`，避免覆盖升级期间的新业务数据。
完成恢复并确认服务健康后，由部署管理员执行：

```bash
./update.sh acknowledge-recovery --confirm
```

此命令只解除恢复锁定，不执行数据恢复。再次更新会重新检查发布内容。

## 发布新版本

发布者须先发布与源码提交对应的四个镜像，并包含
`org.opencontainers.image.revision=<完整提交号>` 标签。随后运行：

```bash
python3 scripts/publish-update.py --revision <完整提交号> --version <版本号> --notes <发布说明文件>
git add updates/stable.json
git commit -m "Publish SkyShield stable update"
git push origin main
```

发布脚本确认四个镜像可以匿名读取、平台为 `linux/amd64`、摘要及源码版本匹配，
才生成稳定渠道文件。渠道依赖 GitHub HTTPS 信任，不额外宣称有发布签名验证。
渠道文件必须在配套代码和镜像发布完成后生成；只有该文件公布的版本才进入自动更新渠道。

本次发布完成源码静态检查及镜像构建，尚未在实际部署环境执行完整升级、断线恢复或
数据库恢复测试。现有部署不会因本次源码修改而自动执行安装。
