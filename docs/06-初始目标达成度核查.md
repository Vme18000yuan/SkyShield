# 初始目标达成度核查

核查日期：2026-10-30。范围：当前 `SkyShield` 源码、两份本地上游源码，以及前一轮实际执行的构建和集成测试结果。

**结论：最初的完整产品目标尚未达成。当前已经形成有真实实现的融合开发版本，但不能按“ARTEX 与 LunaFox 完整功能对等、资产互通、企业级可运行交付”验收为完成。**

此前每轮汇报的完成项是对应子模块的增量交付。源码已复制、菜单已出现、编译与局部集成测试通过，分别是阶段证据；完整交付还需要下列业务能力和真实运行验收。

## 1. 采用的原始范围

以用户后续明确的版本为准：基于 LunaFox 开发，融入 ARTEX Agent 能力；代码落在新建的 `SkyShield` 目录，产品名称为“天穹”；保留 LunaFox 前端设计风格；新增 AI 工作台中的对话、工具执行、AI 任务、AI 计划任务；新增与 ARTEX 对等的资产功能及 LLM、Agent、MCP、Skill、工具设置；传统扫描与 AI 读写资产互通。最初提出的统一 Go 核心、前端、资产库、调度、租户和权限也仍属于整体产品目标。

| --- | --- | --- |

## 4. 阻断整体验收的关键事实

### 4.1 AI 的实际测试执行能力还不完整

默认内建平台能力主要是搜索资产、登记资产和任务探索图操作；管理员可以通过远程 MCP 增加动作。隔离的宿主文件、命令和目标网络执行器尚未交付，因此当前默认 Agent 的规划、事实记录与资产读写能力，仍不足以证明能像完整 ARTEX 一样独立进行深入测试。

证据：[平台工具解析器](../server/internal/airuntime/asset_tool.go)、[任务工具装配](../server/internal/airuntime/task_runner.go)、[ChatRunner](../server/internal/airuntime/chat.go)。

### 4.2 原生扫描存在，但尚未连成内建 AI 任务闭环

继承的 LunaFox MCP 中已经有 [start_scan 适配器](../server/internal/mcp/adapters/scan_operation.go)和原 Scan 应用服务。这不应被误报为“平台没有原生扫描接口”。

当前 AI wiring 注入的 `platformTools` 仍来自 `AssetToolResolver`，尚未看到内建的 AI 任务/意图 → Scan 关联及扫描结果唤醒 AI 规划的接入链路。实施方案中的“AI 发起扫描 → 原调度执行 → 统一入库 → AI 消费结果继续推进”仍未完成验收。

### 4.3 资产互通有真实实现，风险闭环仍有限

[资产登记仓储](../server/internal/modules/assetregistry/repository/asset_registration.go)在同一事务中调用旧资产应用能力、登记统一实体、保存观测和关联任务；旧资产表还具有注册触发与历史回填。这个融合方向已经落地。

但新资产页面尚无完整 ARTEX 资产详情和管理能力；[风险投影 SQL](../server/cmd/server/migrations/000014_ai_task_graph.up.sql)要求关联 Target 和 HTTP service/endpoint 锚点，不能覆盖所有发现、证据、报告与复测。

### 4.4 多租户仍只有基础表和默认数据范围

[DefaultTenantID](../server/internal/modules/assetregistry/application/asset_registry_ports.go)明确是当前唯一支持的数据范围；[JWT Claims](../server/internal/auth/jwt.go)没有租户上下文。新模块的账号隔离测试通过，不能替代原扫描、资产、MCP、文件、日志、导出和后台任务的完整多租户/RBAC 验收。

### 4.5 完整部署与真实业务验收尚缺

已有源码 Compose，但扫描 Agent 仍依赖固定的 daemon 卷名；[卷归属检查](../scripts/tianqiong-volume-preflight.sh)用于避免使用其他部署的数据。当前没有完整天穹栈成功启动及完成扫描的验收证据。本次检查未发现 `tianqiong` / `skyshield` Compose 项目有运行中的容器，常用前后端端口 3000/3001/8080/8081 未监听。

前一轮通过的验证包括 Go 构建、Next.js 生产构建、类型/ESLint/UI/架构守卫，以及隔离 PostgreSQL 的迁移和 AI 集成 race 测试。[测试 Provider](../server/cmd/server/ai_task_runtime_integration_test.go)按预设步骤产生工具调用，这能证明链路正确性，尚不能证明真实模型的规划效果、扫描执行效果或几百个目标下的有效测试覆盖。

## 5. 建议的后续验收顺序

1. 建立可重复的独立运行环境，用真实模型、明确授权的本地测试目标和原扫描节点，完成“组织/目标 → 传统扫描 → 资产 → AI 分析/测试 → 发现与证据 → 风险页面”的一条完整业务链。
2. 完成受控执行器及内建 AI → Scan 的任务关联、结果消费与恢复，验收取消、暂停、迟到结果和重复提交。
3. 按原功能对等清单补齐 AI 设置、完整资产管理和任务生命周期；逐项同时交付后端、前端、数据和行为验收。
4. 完成所有旧模块的租户/RBAC 约束、统一调度治理以及双租户端到端隔离验收。
5. 完成天穹独立版本管理、发布/升级身份和备份恢复演练，形成可安装、可启动、可验收的交付包。

整体完成的判定必须回到[实施验收用例](04-实施阶段与验收计划.md)，尤其是真实 AI/Scan 闭环、资产一致性、权限边界和运行交付。当前只能将已实现的子能力标记完成，整体状态仍应保持“编码实施中”。
