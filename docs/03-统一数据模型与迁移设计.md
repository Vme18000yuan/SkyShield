# 统一数据模型与迁移设计

本文描述目标模型和迁移规则，不是已执行的 DDL。具体 SQL 将在各实施阶段与实际仓储代码、约束测试一起提交。

## 1. 数据所有权

采用 **保留 LunaFox 类型明细与快照 + 增加统一资产身份、类型扩展和来源关系** 的方案。

统一资产库不等于“所有字段挤进一张大表”，也不等于“把两个数据库接到同一个 PostgreSQL”。所有资产经过同一个应用入口，字段只有明确的写入所有者：

| 数据 | 事实源与写入所有者 |
| --- | --- |
| 租户内资产身份、跨目标去重、业务组织归属 | 新 `asset_entity` 及关系表，由 AssetRegistry 应用服务拥有 |
| 原 Website/Endpoint/HostPort 等当前明细 | 原 LunaFox 类型表及 Facade；新 AI 命令通过同一 Facade/事务接口投影 |
| 原扫描历史 | 原 `*_snapshot`、`scan/scan_task`，由原 ResultIngest 拥有 |
| ARTEX 新增的应用、DNS 记录、非 HTTP 服务、方法/参数等 | 新类型扩展/观测表，由 AssetRegistry 拥有 |
| AI 图、事实、目标、意图、上下文和任务配置 | `ai_*` 表与受控 Transcript/Artifact |
| AI 测试与资产的关系 | 明确 FK 关联统一资产 ID，不能只把 URL 写进消息正文 |
| 漏洞及复测 | 原风险表保留；AI 发现/证据扩展和风险关联由 Security 应用边界拥有 |

不再保留 ARTEX `assets` 作为另一套可写主表。ARTEX DTO 和工具可以继续呈现六类资产，但背后的查询适配到统一模型。一次迁移所用临时 staging 表只用于导入、校验及重放，不能成为产品第二个数据源。

## 2. 现有表的关键约束

| LunaFox 对象 | 当前关键字段/约束 | 对融合的约束 |
| --- | --- | --- |
| `organization` | 软删除，存活名称唯一 | 业务组织，不能冒充租户 |
| `target` | `type/name` 存活唯一；domain/ip/cidr 类目标 | 目标代表发现/扫描范围，和资产实体不是同一个概念 |
| `organization_target` | 组织与目标多对多 | 同一租户内可以多个组织共享目标 |
| `subdomain` | `(dns_name, target_id)` 唯一 | 只有域名，不包含 DNS RR 类型/值 |
| `host_port_mapping` | `(target_id, host, ip, port)` 唯一；host 非空、IPv4 `/32`、端口 1～65535 | 不能填假 host、假端口或 IPv6，缺少应用协议/传输协议时保留未知 |
| `website` | `(url, target_id)` 唯一 | 原 URL 原样保存；不可为融合而归一化 |
| `endpoint` | `(url, target_id)` 唯一；无 method | 旧 URL 观测不能证明方法，多个 AI 方法不能被合并 |
| `directory` | `(target_id, url)` 唯一 | 目录证据不自动等同 API 接口 |
| `screenshot` | `(target_id, url)` 唯一，独立 image blob | 列表不拉 blob；身份关联以精确 URL 为依据 |
| `vulnerability` | `(target_id,url,vuln_type,severity)` 唯一，`reviewed` 布尔值 | 不足以完整表示 ARTEX 的发现处置状态和多资产证据 |
| `*_snapshot` | 由 Scan 维度记录，部分为分区表 | 保留扫描历史与当前态的不同生命周期 |
| `scan_task` | Agent assignment、Session/Epoch、冻结计划 | AI 图中的 intent 不能代替原扫描执行任务 |

Website/Endpoint 当前有效数值类型必须叠加 `000008` 迁移读取：`status_code/content_length` 为 BIGINT；响应头/体与截断标志不能在转换时丢失。Go 使用 int64/可空值；前端若数值超过安全整数，DTO 明确以字符串表示，不能默默损失精度。

## 3. 租户、成员、权限与基础表

### 3.1 组织与租户分离

`tenant` 是安全隔离边界；`organization` 是业务归属。一名用户可加入多个租户，一个租户可包含多个业务组织。

| 新表/扩展 | 主要字段和约束 |
| --- | --- |
| `tenant` | `id UUID`、显示名、状态、配额策略、创建时间 |
| `tenant_membership` | `tenant_id/user_id/status/authz_version`；唯一 `(tenant_id,user_id)`，FK 指向 `auth_user` |
| `role`、`permission`、`role_permission`、`membership_role` | 系统预置权限，角色可按租户配置；授予行为审计 |
| `resource_grant` | 可选组织/目标资源范围，不以菜单隐藏实现授权 |
| `service_principal` | 后台计划/集成身份及租户范围、启停和版本 |
| `audit_event` | 租户、操作者、动作、资源、请求/Run、结果、时间和脱敏摘要 |
| `secret_reference` | 租户、用途、加密密文、key_version、轮换信息；普通查询不返回明文 |
| 原业务表 `tenant_id` | 组织、目标、资产、扫描、快照、风险、通知、导出授权、AI 资源等均有可验证租户归属 |

账号沿用 `auth_user`，不复制 ARTEX 的全局密码和 JWT。用户登录后切换租户需服务端验证成员关系，再签发带租户与授权版本的会话或生成可信请求上下文。客户端 `X-Tenant-ID` 只是请求选择，不能直接成为授权依据。

首个迁移把所有已有业务数据归入一个默认租户，保留原共享关系；不能按 organization 拆租户，否则共享目标会被拆坏。请求缺少租户或成员失效时拒绝访问，不在运行时自动回退默认租户。

### 3.2 数据层强约束

- 业务表增加 `UNIQUE(tenant_id,id)`，关系 FK 使用 `(tenant_id,parent_id)` 指向同租户父对象；唯一约束中的业务自然键加入租户，例如存活 Target 的 `(tenant_id,type,name)`。
- 关系表如 `organization_target` 增加 tenantId 和两侧复合 FK；禁止跨租户挂载，即使上层代码漏检也不能写入。
- Repository 接收可信 Context，读取、计数、搜索、导出、删除、批量更新和关联查询全部约束租户，不能只改列表查询。
- 当前部分应用函数忽略 `ctx` 或仓储没有 Context；按调用链补齐，不能声称增加中间件即完成隔离。
- 多租户生产开启 PostgreSQL RLS 作为第二道约束。事务内用 `SET LOCAL`/事务级 `set_config` 设置租户；使用非 superuser、非 BYPASSRLS 的业务角色，并按适用表 `FORCE ROW LEVEL SECURITY`。不在池连接上永久设置租户。
- 全局调度仅使用最小权限查询待处理租户/Job，具体业务操作再进入租户事务；迁移身份、平台运维身份与普通请求身份分开。
- 针对现有分区快照，逐表验证父表访问与直接访问分区的隔离，直接分区权限不能成为旁路。

### 3.3 权限粒度

建议初始角色：租户管理员、资产管理员、安全分析员、只读审计员；平台运维角色与业务租户成员分开。

必须区分：资产读取/登记/删除、扫描执行、AI 对话/任务执行、工具执行、AI 设置修改、凭据使用/查看、审批决策、证据导出、成员管理。`ai.settings.write` 不自动获得 `tool.execute` 或任意凭据的查看权限。

后台计划绑定服务主体和授权范围，每次执行重新验证启用状态和权限版本。撤销成员/凭据/工具权限影响后续调用及活跃订阅；不能因为任务创建时有权限就永久继承。

## 4. 统一资产表族

### 4.1 主体、类型扩展与关系

| 表族 | 关键字段及用途 |
| --- | --- |
| `asset_entity` | `id BIGINT`、`tenant_id`、`type`、`identity_key`、`identity_hash`、`identity_version`、`first_seen_at/last_seen_at`、生命周期；六类统一身份 |
| `asset_domain` | 根域名/子域名的域名、根域名关系；DNS RR 类型未知与已知分开 |
| `asset_dns_observation` | RR 类型、值、解析来源、TTL、观测时间和证据；多值不相互覆盖 |
| `asset_ip` | `ip INET`，IPv4/IPv6，网段派生信息；域名绑定和端口由关系/观测查询生成 |
| `asset_application` | 平台/命名空间、bundleId 或应用名、分类、描述、备案及来源 |
| `asset_service` | HTTP/其他服务分类、原始 URL 或网络身份、domain/ip/port、transport、serviceName、指纹等扩展；未知值有明确状态 |
| `asset_endpoint` | 原始 URL、已知 method 或内部 UNKNOWN 状态，参数定义和认证引用；不替代原 `endpoint` URL 观测 |
| `asset_observation` | 来源系统、来源记录/事件、资产、target/scan/AI task/run/toolCall、observedAt、类型化事实、证据引用、采集状态 |
| `asset_target` | 资产与 Target 多对多，关联原因、观测/派生来源、首末时间 |
| `asset_organization` | 资产与业务组织多对多，显式/范围推导、规则和主归属标志 |
| `organization_scope` | 复用 ARTEX 企业范围算法：domain/ip/cidr/icp/keyword，关联原 organization |
| `asset_relation` | 父子/解析/承载/暴露/方法变体等关系与来源，不把展示包含关系混成同一实体 |
| 类型绑定表 | `asset_website_binding/asset_endpoint_binding/asset_subdomain_binding/asset_host_port_binding/...`；连接原类型记录和统一身份，含绑定角色与复合 FK |
| `asset_external_reference` | 可选上游系统实例、原类型、原 ID → 新 ID 的稳定映射，专用于导入与外部来源 |

主表管理身份和生命周期；旧字段继续由原明细表拥有，新字段进入类型扩展或观测。来源观测保存历史事实，不再创建一张可独立编辑的“完整 ARTEX 资产副本”。列表通过读模型组装六类 DTO；缓存只是可重建投影。

Typed binding 表用真实 FK 约束原记录。外部引用的字符串标识不能替代平台内真实 FK；所有建立/删除关系的应用命令仍做租户和资源检查。

### 4.2 身份规则

资产 ID 与原表 ID 分开。例如 Website 17 对应 `assetEntity=89`，这个映射显式存储；不能拿 17 到另一张资产表直接查询。

| 类型 | 新统一身份依据 | 注意事项 |
| --- | --- | --- |
| 根域名 | 租户 + root_domain + DomainKey 域名 | 可复用 ARTEX DomainKey/公共后缀算法；保留原始观测值 |
| 子域名 | 租户 + subdomain + 域名 + DNS RR 类型或 UNKNOWN | 未采集 DNS 类型不猜 A；A/AAAA 按 ARTEX 语义可区分，域名视图可聚合 |
| IP | 租户 + ip + 解析后的标准 IP 主机地址 | IPv4-mapped IPv6 的处理显式固定；不把 CIDR 范围等同某个 IP |
| 应用 | 租户 + app + 平台/命名空间 + bundleId；无 bundle 时使用应用名身份 | 上游未给平台时使用明确 unknown 命名空间，后续补全通过显式合并而非静默换 ID |
| HTTP 服务 | 租户 + service/http + **完整原始 URL** | 不改变旧原始 URL；归一化 host/origin 只用于检索、关系或候选合并 |
| 其他服务 | 租户 + service/other + host/ip/port + transport + serviceName | 未知协议/服务名显式保留；补全产生候选等价关系，不无证据合并 |
| 接口 | 租户 + endpoint + **完整原始 URL** + method/UNKNOWN | 已知方法大写；UNKNOWN 是内部状态，不能作为真实 HTTP 方法发送 |

`identity_key` 使用版本化、无歧义编码的类型化字段，例如稳定 JSON 数组；不能用简单字符串拼接产生分隔符碰撞。长 URL 使用摘要索引，`UNIQUE(tenant_id,type,identity_hash)` 冲突后校验完整 key，相同才复用，摘要碰撞明确报错而非合并。保存原始 URL 和来源，禁止用 hash 代替证据。

前端/AI 工具返回资源名或十进制字符串 ID，新增 BIGINT 不能未经判断转为 JavaScript Number。原 LunaFox 数字 ID 的兼容边界仍由原端点控制。

### 4.3 原始 URL 和归一化的裁决

保留 LunaFox 的证据规则：接受的 URL 原字符串不 trim、不解码、不做大小写折叠、不去尾斜线、不重排 query、不模板化路径。ARTEX `normalizeURL` 仅可改造为候选匹配/索引派生算法，不能用于统一观测主键写入。

因此 `https://a.example/` 与 `https://a.example` 可暂保留不同观测身份，UI 可以显示同源关系；`/User/1` 与 `/user/1`、`%2F` 与 `/`、不同 query 的地址不能无证据合并。模板化路径仅供分析视图，不作为旧观测身份。

### 4.4 无损字段映射

| LunaFox / ARTEX 来源 | 统一结果 | 原视图的处理 |
| --- | --- | --- |
| domain Target | 精确目标域名对应根域/子域实体，根域关系按公共后缀算法派生 | Target ID、名称和类型保留；域名目标不一律当作根域名 |
| IP Target | IP 实体和 target 关联 | 保留原范围和目标管理 |
| CIDR Target | 授权/发现范围 | 不为每个潜在地址预建资产；只为真实观测到的地址建 IP |
| `subdomain.dns_name` | 子域实体，RR=UNKNOWN；保留原记录绑定 | 原子域列表正常读取；后续 DNS 信息进入观测扩展 |
| `host_port_mapping` | IP + 端口观测 + host 关系；足够字段时建立服务实体 | 原 IPv4 明细保持；不从端口号猜测已验证的应用服务 |
| `website.url/title/status_code/tech/...` | HTTP 服务身份 + 原 Website 绑定 + HTTP 证据 | title→pageTitle、tech→technologies；原字段精度及截断标志完整保留 |
| `endpoint.url/...` | method=UNKNOWN 的接口实体及原 Endpoint 绑定 | 旧 URL 明细仍一行；实际方法变体通过扩展关联展示 |
| `directory` | URL 路径观测/附加证据，关联相应服务或已知接口 | 不强制当作已确认 API 端点 |
| `screenshot` | 精确 URL 的截图证据关联 | image 留在原存储；列表只给元数据/受控读取引用 |
| ARTEX app | application 扩展 | 原 LunaFox 没有对应表，统一资产页可直接看到；不制造虚假域名目标 |
| ARTEX root_domain/ip/subdomain/service/endpoint | 对应统一实体及观测 | 可投影的字段写回原类型视图；额外字段保存在扩展 |
| ARTEX company/company_scope | 原 organization + organization_scope + 资产组织关系 | 不新建第二套 companies 主数据 |
| ARTEX task_ids | 关系表计算的任务集合 | 可在 ARTEX 风格 DTO 投影，不能再作无 FK 的主要归属依据 |
| ARTEX bound_domains/open_ports | 关系/观测集合的读投影 | 保留多值及来源，不用某次空数组覆盖已有集合 |
| ARTEX auth/credentials | 授权凭据引用 + 脱敏认证摘要 | 密码/Token 不直接放入普通资产响应或活动日志 |

缺失值有 `unknown/not_collected/observed_empty` 等可区分的采集状态。NULL、空串、空数组并非同义，模型不得用“没看到”覆盖已有非空事实。

### 4.5 Endpoint 方法冲突的明确处理

示例：旧库有 `endpoint(id=41,target=7,url=https://api.example/orders)`，扫描未采集 method；AI 后续分别测试 GET 和 POST。

1. 旧记录映射到 method=UNKNOWN 的实体 U，不标记为 GET。
2. AI 创建 GET 实体 G 和 POST 实体 P，并分别登记请求、参数、证据与测试结果。
3. 原 `endpoint` 表继续保持 URL 级一行。U 的绑定角色为原生未知方法观测，G/P 可建立 `url_projection` 关联，原页面增加“已知方法变体”入口。
4. URL 级响应摘要只保存能明确解释的公共观测；方法相关响应和认证状态留在各自观测，不能让 POST 覆盖 GET 的语义。
5. 任务明确测试 G 时，仅 G 的事实锚点算作其测试记录；P 和 U 不被自动认定已测试。

该设计保留原表唯一键和读接口，又不损失 ARTEX 方法级能力。若后续决定让原 Endpoint API 原生支持方法，应另做有数据迁移和客户端切换的版本变更。

### 4.6 IPv6 和 HostPort 限制

统一 IP 实体支持 IPv6；原 HostPort 当前 IPv4 约束保留。AI 发现 IPv6 服务进入新 IP/服务观测和统一资产页，不写入旧 `host_port_mapping`，响应明确标注该类投影不适用。将来扩展原协议和表约束时单独迁移及回归。

只有 IP 和端口而没有合法 host 的结果不能填空串绕过约束。是否允许“IP 字面量作为 host”须遵守原类型校验；不满足时保留扩展观测和原因，避免已返回资产 ID 但旧表静默写失败。

## 5. 企业归属和范围

ARTEX 单 `company_id` 与 LunaFox 组织多对多不完全一致。统一使用 `asset_organization`，可包含多个组织归属并标记显式/规则推导、规则 ID、理由、优先级和 primary。

- 复用 ARTEX domain/ip/cidr/icp/keyword 匹配算法，但所有查询限定同租户。
- 显式归属优先，范围重算只重建自己推导的关系，不能删除人工关系。
- 为兼容六类资产 UI，可投影主企业和全部组织；不能用不稳定的“查询第一条”作为主企业。
- 关联来源和授权范围分开建模。资产属于某公司，不自动意味着用户获得该公司所有资产的读取或测试权限。
- 公司/任务 Scope 是发现和覆盖范围；授权 Scope 是执行上限。Agent 可以建议扩大覆盖范围，不能自己扩大已授权目标边界。

## 6. AI 数据表与原表的连接

采用 `ai_` 前缀与 LunaFox 的扫描 `agent/scan_task` 区分。下表是迁移命名及保留语义，实施时拆分字段但不能遗漏功能。

| ARTEX 原表/数据 | 天穹目标表/所有者 | 关键改造 |
| --- | --- | --- |
| `tasks/task_categories/task_templates/task_relations/task_archives` | `ai_task/ai_task_category/ai_task_template/ai_task_relation/ai_task_archive` | 租户、创建人/服务主体、原生命周期、排队/预算、归档来源 |
| `explorations/exploration_nodes/exploration_edges` | `ai_exploration/ai_exploration_node/ai_exploration_edge` | 保留 begin/goal/intent/fact/finding/hint/digest 及边、状态、冷图版本 |
| `exploration_anchors` | `ai_exploration_anchor` | FK 指向统一 assetEntity，节点归属同一租户/探索 |
| `task_asset_links` | `ai_task_asset` | 显式记录发现/继承/选择/测试来源、sourceNodeId，替代主关系数组 |

## 7. AI 测试、覆盖度与风险

### 7.1 测试记录不能等同资产存在

ARTEX 原覆盖度定义是“Scope 内资产中，至少锚定到一个 fact 节点的比例”，源码明确它是粗略参考，不是精确安全覆盖率。天穹保留该指标、类型分组、分母为零时 null、未测清单和图展示，中文名称为“探索覆盖度（约）”。

同时增加可审计的 `ai_asset_test` 记录：

`tenant_id + ai_task_id + run_id + intent_id + asset_id + test_kind + tool_execution_id + status + verdict + evidence_ref + started_at/finished_at + config_revision`。

`status` 区分待执行、运行中、完成、失败、取消、结果未知；`verdict` 区分存在问题、未发现问题、证据不足、不适用。任务创建、查询资产、插入资产、范围自动扩展都不自动写成“测试完成”或“安全”。

测试活动与 fact 锚点可以一并关联，但不能把旧粗略覆盖度改称“已验证无漏洞”。继承测试结果保留来源与时间，不默认当作本次新测试。按任务 Scope 动态计算的分母与可选冻结样本分母分别解释，不混用。

### 7.2 风险归并

AI finding 的处置状态比 LunaFox `reviewed` 丰富，不能直接压缩成布尔值。保留 `ai_finding`、多资产关联、原始证据/版本、报告和复测，并用 `risk_finding_link` 关联原 `vulnerability`。

- 可定位到授权 Target/URL 的发现，通过 Security 应用服务登记原风险投影，`source=ai`，保留 AI 原 ID 和证据关系。
- App 或无 Target 的发现先存在统一 AI 风险扩展与风险聚合列表，不制造假 URL/目标；聚合响应明确来源，原漏洞列表接口继续兼容。
- 对同一问题的候选归并基于资产、位置、漏洞类别和证据，不只比较标题。原 vulnerability 唯一键的 severity 含义仍保留，不粗暴删除索引。
- 人工 `reviewed`、finding 处置、复测 verdict 各自有独立语义；一次复测“未复现”不能自动设为已修复。
- 同一发现经 AI 任务页和风险页读取时使用同一关系和状态服务，不能各自修改互不通知。

## 8. 统一写入与读回链路

### 8.1 扫描发现 → AI 可读

1. 保留原 `ResultIngestFacade.Ingest`，验证批次格式和执行 Scope。
2. 在现有事务内锁定活动 Target、Scan、Agent Session/Epoch、scan_task。
3. 原 materializer 写扫描快照与类型当前态；新增资产登记适配器在**同一事务 Context**登记实体、绑定、来源及 target 关系。
4. 刷新原扫描统计，写事务 outbox；提交后通知 AI/搜索投影。
5. AI `list_assets` 在同租户、同授权/任务 Scope 下读取统一实体和原明细。

一次扫描批次原本是原子提交，保持这一性质。登记失败必须连同本批快照/当前态回滚，不能记录“扫描成功但 AI 永远看不到”。

### 8.2 AI 发现 → 原资产视图可读

1. ARTEX `insert_assets` 解析原输入结构，服务端附加可信 RunContext。
2. 统一准入检查租户、目标授权、资产拦截规则、类型和字段，解析显式或可唯一判定的已有 Target。
3. 每个输入项在一个事务中完成实体 upsert、类型扩展、观测、组织/Target/任务/节点关系，以及适用的原类型表投影。
4. 能投影到原 Website/Endpoint/Subdomain/HostPort 的数据经 Facade 写入；App、IPv6 或缺少必需字段等明确“不适用”的投影保留扩展和原因。无法唯一判定 Target 时先登记待关联关系，不任意选一个也不擅自扩大扫描范围。
5. 提交后返回原 ARTEX 风格 `results:[{index,id,type}],errors:[...]`；新附加信息可提示 target/projection 状态。成功 ID 必须已提交；预期可投影的旧表写失败时，本项回滚并返回错误。

ARTEX 插入工具允许逐项成功/失败，因此不同输入项可以分别提交；不能误改成整个工具批次任一项失败全部撤销。原扫描批次与 AI 工具批次的事务单位不同，但每个已承诺成功的业务单位内部都保持一致。

### 8.3 手工/外部导入及直接旧页面写入

旧资产页面、AI 工具、可选 ScopeSentry、导入命令最终进入同一个登记服务或经过可验证的同事务登记钩子。需要盘点原新增、更新、删除、批量操作、cleanup 和恢复链路，不能只接扫描和 AI 两条入口。

一次性回填之外，后台 reconciliation 定期验证孤立绑定、缺少实体的原记录和投影版本，用于修复或报警，不是两套资产主库间的日常双向同步机制。

### 8.4 幂等、冲突与字段优先级

- 原扫描结果维持原批次/自然键去重，新增登记与相同事务重复调用保持幂等。
- AI 工具使用服务端分配的 `runId/toolCallId/itemIndex` 作为来源幂等键；任务/会话/租户也纳入命名空间。
- 原始观测按来源保存，最新字段按观测时间和明确来源优先级投影；空值缺失不覆盖。冲突保留来源，不默默选择最后收到的数据。
- 人工业务字段、处置状态和显式归属优先，模型观测不能覆盖人工风险决策。
- 同一资产跨 Target 是同一 tenant 内一个实体、多组观测与关联；跨 tenant 即使同域名/IP 也分别建实体，不能通过去重泄露其他租户的存在。
- outbox 消费者按 `(tenant,eventId,consumer)` 幂等，事件携带版本；旧事件不能覆盖新版本投影。

## 9. 删除、恢复和共享资产

删除 AI 任务默认删除/归档其运行状态和关系，不直接删除被原扫描、其他任务或组织引用的共享资产。ARTEX 的“删除关联资产”能力需改为受控清理：展示可删除/保留的实际依赖统计，仅清理没有其他所有权和保留要求的记录。

Target 软删除仍走 LunaFox 既有 cleanup 工作流。新增 registry 解除该 Target 的绑定，其他 Target/AI 来源仍引用的实体保留；快照及证据按各自保留策略处理，不能因当前资产删除而无提示破坏历史报告。

业务合并/去重需要保留 oldId→newId 映射并原子更新图锚点、测试、风险、文件和外部引用；不能直接删掉重复实体。恢复归档时验证租户与引用，不覆盖已有人工状态，也不自动继续未知副作用的工具调用。

## 10. 调度与运行持久化

新增 `execution_job`：租户、业务种类、业务引用、Run、状态、leaseOwner/leaseEpoch/leaseUntil、attempt、dedupeKey、配额、requestId 和时间。`schedule_occurrence` 记录具体交付动作；扫描已有 occurrence 可通过适配器参与统一协调，首阶段不强制搬表。

AI 运行窗口另存原 once/weekly、timezone、时间段、endDate、task links、manualUntil、pausedBySchedule 和 transition history。时间戳统一 UTC/TIMESTAMPTZ，窗口解释使用 IANA 时区；ARTEX `beijing` 映射 `Asia/Shanghai`，`system` 在导入时解析并固化原部署时区，避免迁移后宿主时区改变。

工具执行账本唯一性包含 `tenant/run/toolCallId`。配对 tool_use/tool_result 时必须限定来源、会话/探索和 Run，不能只按可能复用的 tool_use_id 连接。未知结果单独状态，不把“没有结果记录”默认为成功。

## 11. 迁移策略

### 11.1 新安装和已有数据分别处理

1. 锁定两个上游提交，保留 LunaFox 原 `000001`～`000009` 和摘要。
2. 在 SkyShield 新增后续编号迁移（从 `000010` 开始规划，实际连续编号以提交时状态为准），分别承载身份、资产、AI、调度等增量。
3. 统一清点 ARTEX DDL：包括 `schema.sql` 以外的 usage、record、traffic/credential 等存储；进入统一迁移/证据存储初始化清单。业务启动不重跑旧 `db.Open`。
4. 干净库路径完整运行原迁移与天穹迁移；存量路径先备份，停写或进入明确维护窗口，再扩展 nullable 列/表、分批回填、验证并加约束。
5. 回填以稳定旧主键游标与检查点推进，记录每种类型计数、歧义、失败及映射。域名/URL 冲突不因回填中断而丢掉原记录。
6. 验证所有必要绑定、跨表 tenant FK、未知方法、IPv6、原始 URL、风险/图/测试引用后切换读写。
7. 完成回填后新写入必须通过登记接口，取消运行时默认租户和其他过渡兼容入口。

LunaFox 当前上游迁移策略没有承诺普适保留数据升级；天穹新增迁移必须自行实现并演练，不能继承一个并不存在的保证。天穹使用自己的发布 manifest/检查器，既保留原历史字节，又不拿上游“每次发行最多一个增量”的生成器未经改造来发布多个天穹阶段。

### 11.2 可选 ARTEX 存量导入

当前没有用户现有数据库连接信息，不能假定已经完成导入。导入器先只读 preflight，读取源版本、类型/记录数和字段覆盖，生成 dry-run 报告。

需要保留 `sourceSystem + sourceInstance + oldId → newId` 映射；公司匹配到已存在组织时不只靠名称猜测，可人工指定冲突映射。资产按租户身份去重，任务/图/发现/活动/归档与 JSON 引用统一重映射。Transcript、流量、Skill、附件另有文件清单、摘要及引用重写。

导入过程可续跑、幂等、输出逐项错误与核对统计。新系统接收并验证完成前不写源库、不删除原数据。导入中的运行任务先标记为待恢复，不能在新环境自动继续未完成的外部操作。

### 11.3 恢复与验证门槛

生产恢复通过已验证的数据库与相关文件快照恢复或前向修复，不依赖 down SQL 保留数据。恢复演练要涵盖资产、AI 图、LLM 计量、审批、Transcript、流量证据和 Skill 版本，而不仅是 PostgreSQL 表。

迁移验收至少包括：幂等重跑、回填中断续跑、重复身份、跨 Target、跨租户同名数据、原始 URL、UNKNOWN/GET/POST 分离、IPv6、弱空值、BIGINT、复合 FK、图/风险引用、共享资产删除及备份恢复。
